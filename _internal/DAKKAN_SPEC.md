## 1. 何を作るのか

**店頭で「他社から乗り換えたら、いくらどう変わるか」を、その場で数字にして見せる道具。**

いま店頭では、お客様の請求書を見ながら口頭と電卓で説明しています。数字が残らないので、お客様は持ち帰って検討できません。ケータイ見積もりが「ドコモにしたらいくらか」を1枚にしたのと同じことを、**「いまのご契約と比べてどうか」**についてやります。

### 使う場面

| # | 場面 | 出したいもの |
|---|---|---|
| A | 他社ユーザーが来店した（**奪還**） | いまの支払い vs ドコモにした場合。乗り換えに掛かる費用と、何か月で追いつくか |
| B | 光・でんきも他社（**イエナカ連動**） | スマホだけでなく、光・でんきまで含めた世帯の比較 |

### 完成の判定

**「お客様が持ち帰って家族に説明できる1枚」が出ること。** 口頭の補助ではなく、紙として成立していることが条件です。

## 2. どこに作るか

### 結論：`dakkan-app/` として単体で作る。ただし**最初から統合を前提にした書き方**にする

イエナカは単体アプリとして作ったあとでケータイ製品版へ統合しました。そのとき **idが24個ぶつかって全部リネームする作業**が発生しています（`_internal/IENAKA_MERGE.md` 参照）。同じことを繰り返さないために、**最初から次を守ってください。**

1. **画面のidは全部 `dk` 接頭辞にする**
   `carrier` ではなく `dkCarrier`、`monthly` ではなく `dkMonthly`
2. **`data-` 属性も `dk` 接頭辞にする**
   `data-opt` ではなく `data-dkopt`
3. **計算と画面描画を、保存・同期・ログインから切り離しておく**
   イエナカでは `calc()` が `state` と `save()` に直結していたため、切り出すのに手間が掛かりました。
   最初から次の形にしておいてください。

```js
window.KQ_DAKKAN = {
  defaultState: defaultState,   // 入れ物の初期値
  attach: function (state, onChange) {},  // 外から状態を渡す
  bind: bind,                   // イベント登録（1回だけ）
  syncForm: syncForm,           // 状態 → 画面
  calc: calc,                   // 計算（画面に触らない）
  render: render,               // 画面の表示だけ
  sheetHtml: sheetHtml          // 見積書の中身（表題・発行元は呼び出し側が付ける）
};
```

`keitai-app/ienaka.js` が**まさにこの形**なので、そのまま手本にしてください。

### ファイル構成（`dakkan-app/`）

```
dakkan-app/
  index.html
  app.js            ← 単体で動かすための入れ物（ログイン・保存・担当者）
  dakkan.js         ← 計算と画面。window.KQ_DAKKAN を公開する（統合時はこれだけ移す）
  data.js           ← 他社の料金・手数料（マスタ設定で編集できる）
  style.css
  sw.js
  manifest.webmanifest
  icon.svg
  firebase-config.js
```

`app.js` と `dakkan.js` を分けるのが肝です。**統合するときは `dakkan.js` と `data.js` だけを移せば済みます。**

## 3. 画面と機能

### ① いまのご契約

お客様の請求書を見ながら入力します。**入力の手数を減らすことが最優先**です。店頭は時間がありません。

| 項目 | 形 | 備考 |
|---|---|---|
| キャリア | 選択 | au / SoftBank / 楽天モバイル / ワイモバイル / UQ mobile / MVNO |
| プラン名 | 入力（任意） | 引き継ぎシート用。計算には使わない |
| 月々のお支払い | 入力 | **請求額をそのまま入れる。** 内訳は聞かない |
| うち端末の分割 | 入力 | 残債の判定に使う |
| 残りの回数 | 入力 | 〃 |
| 家族の回線数 | 入力 | みんなドコモ割の判定に使う |
| 光・でんきのセット割 | チェック | 他社側で付いているもの。乗り換えで失う |
| キャリアメール | チェック | 持ち運びの費用が掛かる |

### ② 乗り換えに掛かるもの（出ていく側）

**ここが「奪還」の肝です。** お客様が一番気にするのは「解約金がいくらか」で、実際にはほとんど掛からないのに誤解されています。それを数字で見せます。

| 項目 | 扱い |
|---|---|
| MNP転出手数料 | **各社の現行値を一次情報で確認して data.js に入れる** |
| 契約解除料 | **プランによって有無が違う。** 旧プランに残っている場合がある。要確認 |
| 端末の残債 | 一括で払う／分割を続ける の2通りを出す |
| キャリアメール持ち運び | 各社の月額。要確認 |
| その他 | 店舗が自由に追加できる欄を用意する |

### ③ ドコモにした場合

**ケータイ見積もりの結果を使います。** 二重入力させないこと（第7章の連携を参照）。

### ④ 比べる

出す数字は3つだけにしてください。多いと伝わりません。

```
いまのお支払い          9,800円/月
ドコモにした場合        6,908円/月    −2,892円/月
乗り換えに掛かる費用    3,850円（事務手数料）＋端末残債 24,000円
────────────────────────────
◯か月で追いつきます
```

「◯か月で追いつく」は **(乗り換え費用) ÷ (月々の差額)** です。差額が0以下のときは出さないこと（追いつかないのに数字を出すと嘘になります）。

### ⑤ 解約新規の判定 —— 保留

**この画面は作りません。** 2026-07-29 に安藤さんの判断で保留になりました。
再開することになったときのために、設計の考え方だけ第6章に残してあります。

## 4. 料金データの扱い（絶対に守る）

このリポジトリの一貫したルールです。

1. **一次情報（各社の公式サイト）で確認できた値だけを入れる。**
2. **確認できなかったものは空欄にして、店舗に登録してもらう。** 推測した数字を入れない。
   （でんき・ガスの連絡先で、確認できなかった5社を空欄にしたのと同じ扱いです）
3. **出典URLと確認日を `data.js` にコメントで残す。**
4. **すべてマスタ設定から編集できるようにする。** 他社の料金は頻繁に変わります。
5. **画面と見積書に「料金データ基準日」を出す。** 古い数字で比較すると、そのままクレームになります。

確認しに行く先（2026-07 時点の想定。実際のURLは各社サイトで辿ること）:

- au … MNP・解約に関する手数料のページ
- SoftBank … 同上
- 楽天モバイル … 同上
- ワイモバイル / UQ mobile … 同上
- ドコモ … 契約解除・新規契約の条件、dポイントクラブの継続期間の扱い

**自動取得（スクレイピング）はアプリに入れないでください。** 各社の規約と安定性の問題があります。値は人が確認して data.js を更新する運用にします（ドコモのRSS監視と同じ考え方。`_internal/RSS_WATCH.md` 参照）。

## 6. 注意（販売する以上、ここは外せない）

### 解約新規について（保留・再開するときの覚え書き）

**2026-07-29 に保留となりました。いまは作りません。**

再開の判断材料として、保留の背景を残しておきます。

**解約新規は、代理店とドコモの取り決めによっては制限されていることがあります。**
ツールが「解約新規を勧める道具」に見えると、**代理店が導入できないどころか、売る側のリスクになります。**
製品版と抱き合わせで販売する前提なので、ここは慎重に決める必要があります。

再開する場合に守ること:

- **既定は「継続」。** 解約新規は選んだときだけ出す
- **失うもの**（電話番号が変わる／契約の継続年数がリセットされる／dポイントクラブのランク・長期利用の特典／
  ドコモ光セット割・みんなドコモ割の再申請／キャリアメールのアドレスが変わる）を、
  **得るものと同じ大きさで、同じ画面・同じ紙に出す**
- 「おすすめ」「有利」といった断定の言葉を使わない。**数字を並べて、判断はお客様と担当者に委ねる**
- 実際に何が失われるかは、その時点のドコモの規約を確認して `data.js` に持たせる（店舗が編集できる形に）

こうしておけば「正しく比較するための道具」として説明できます。
**再開するときは、まず安藤さんに「どこまで踏み込むか」を確認してください。**

### 他社の料金を扱うこと

- 基準日を必ず出す（第4章）
- 「他社の公式な案内ではない」旨を、ケータイ見積もりの `TERMS.md` 第2条と同じ形で入れる
- **お客様の請求書の内容は個人情報です。** ケータイ見積もりと同じく、**お客様名はクラウドへ送らない**ルールを守ってください（`keitai-app/app.js` の `quotePayload()` が参考になります）

## 7. ケータイ見積もり・イエナカとの連携

### 7-1. いますぐ使える方法（単体アプリのまま繋ぐ）

**`kq-handoff-v1` の仕組みが既にあります。** 同じドメインに置いたアプリ同士が、localStorage 経由で店舗名・担当者名・お客様名を渡し合うものです。

- 書き出す側 … `keitai-app/app.js` の `initIenakaLink()`
- 受け取る側 … 同 `takeHandoffFromIenaka()`
- 中身 … `{ from, storeName, staffName, custName, at }`。**10分で期限切れ**にして、読んだら消す

奪還ツールでも同じキーを使い、`from: "dakkan"` を入れてください。ヘッダーに相互リンクを置けば、ワンクリックで行き来できます。

**渡す内容を増やすときは、`custName` 以外にしてください。** お客様名以外の見積もり内容（月額・端末）まで渡すと、handoff が実質的なデータ同期になり、どちらが正なのか分からなくなります。

### 7-2. 最終形（ケータイ製品版のタブとして統合）

イエナカと同じ形にします。**イエナカの実装（1.15.0 / 1.15.1）がそのまま手本です。**

| 決めること | どうするか | 理由 |
|---|---|---|
| 状態の置き場所 | **`store.dakkan`（パターンA/B/Cの外）** | 「いまのご契約」はお客様1人につき1つ。A・B・Cはドコモ側の提案を3通り並べるものなので、比較の相手は共通です。光を `store.ienaka` に置いたのと同じ理由 |
| 保存・同期 | `store` ごと保存されるので自動で付いてくる | ただし**復元の3経路すべて**に通すこと（下記） |
| タブ | `<section id="tab-dakkan">` を足し、タブに「他社比較」 | |
| 見積書 | 切替に「他社比較（別紙）」を足す | 光と同じく、**別紙の1枚**にする。スマホの見積書に混ぜない |
| 引き継ぎシート | 「他社からの乗り換え」欄を足す | 後工程がMNP予約番号・残債の扱いを把握できるように |

**復元の3経路**（イエナカで一度漏らして直した箇所です。必ず全部通してください）:

1. `loadState()` … 起動時
2. `loadSavedQuote()` … 保存した見積もりを開いたとき
3. `applyRemoteQuote()` … 端末間同期で受け取ったとき

`keitai-app/app.js` の `applyIenaka()` が、この3つから呼ばれる共通関数です。同じ形で `applyDakkan()` を作ってください。**入れ物（オブジェクト）は差し替えず、中身だけ入れ替える**こと（モジュール側が参照を握っているため）。

### 7-3. イエナカとの連動

場面Bのためです。**光も他社から乗り換える場合**、比較に光の分も入れる必要があります。

- 光の月額は `KQ_IENAKA.calc()` から取れます（`segs[segs.length - 1].monthly` が通常時）
- **セット割を二重に数えないこと。** ケータイ側の③割引で既に引いています
- 「他社比較（別紙）」に、スマホと光の両方を並べた世帯の比較を出すのが理想形です

### 7-4. 抱き合わせ販売の観点

安藤さんの目的は**製品版との抱き合わせ販売**です。作りながら次を意識してください。

- **別料金のオプションとして売る場合**、機能を出し分ける器が要ります。
  `stores/{uid}/billing` に契約状態を持たせる案が `_internal/OPERATIONS.md` にありますが**まだ実装していません。**
  奪還ツールを統合するときが、この器を作る良いきっかけになります
- **標準機能として付ける場合**、器は不要です。タブを足すだけで済みます
- どちらにするかは価格が決まってからの判断です（利用料金は 2026-07-29 時点で未定）

## 8. 作業の進め方

`CLAUDE.md` の「リリース手順」に従ってください。要点だけ再掲します。

1. `node --check` で構文を確認
2. **Playwright で実際に動かして確認する。** 見た目だけでなく、数字が合っているかを検算する
   ```
   const { chromium } = require('/opt/node22/lib/node_modules/playwright');
   chromium.launch({ executablePath: '/opt/pw-browsers/chromium' })
   ```
   ローカルで動かすときは `python3 -m http.server` を使ってください（`file://` ではダウンロードや fetch が動きません）
3. **紙になるものは `pdfinfo` でページ数を確認する**
   ```
   page.emulateMedia({media:'print'}); page.pdf({format:'A4'});
   ```
   ケータイ見積もりの見積書はA4 2枚、光の別紙は1枚に収めています。**奪還の別紙も1枚に収めてください**
4. `APP_VERSION` と `sw.js` の `CACHE` を必ず両方上げる
5. コミット → rebase → force-with-lease で push → PR（draft → ready → squash マージ）
6. GitHub Pages に出るまで確認してから完了報告

### 検算の例

金額を出す機能は、**手計算と突き合わせてから完了報告してください。**
爆アゲの還元率で、税込から計算していた誤りと切り捨て／切り上げの誤りを2回続けて出しています（`_internal/BAKUAGE.md`）。
